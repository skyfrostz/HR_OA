# 商业交付审查：员工搜索与筛选导出契约

日期：2026-11-07。此文档记录本轮协调确定的接口增量，扩展 `OA_API_CONTRACT.md` 与 `M3_API_CONTRACT.md`。**契约确认不代表实现或验收完成**，完成证据由后端、前端和 QA 分别提交。本轮不修改历史验收结论。

所有路径仍以 `/api/oa/v1` 为前缀，使用内存会话的 `x-token`、既有响应信封、实时账号状态和角色/行/字段权限。旧 GET 员工列表及 GET 导出接口保留原语义。

## POST /employees/search

JSON 请求示例：

```json
{
  "query": "张",
  "departmentId": null,
  "page": 1,
  "pageSize": 20
}
```

- `query` 为字符串，先去除首尾空白，最多 100 个 Unicode 字符。空字符串表示不添加文字筛选。
- 在姓名、工号和部门显示名称之间执行 OR 的字面子串匹配。输入中的 `%`、`_` 等字符不能扩大为 SQL 模式通配范围；不提供正则或用户 SQL 表达式。
- `departmentId` 可不提供或为 `null`，表示不添加部门条件；提供时为正整数，匹配该部门本身，不递归包含子部门。
- 文字、部门条件与既有授权行范围为 AND 关系。员工/审批人即使输入其他人的姓名或部门，也不能扩大本人范围。
- `page`/`pageSize` 沿用既有分页约束：默认 1/20，页大小最多 100，并保留页数/偏移计算安全校验。
- 返回 HTTP 200，`data` 为 `{list,total,page,pageSize}`。员工字段沿用 M3 的 EmployeeView，包括部门关联与版本；无工资权限时完全省略工资字段。无匹配结果返回空列表，不泄露未授权记录是否存在。
- 错误沿用既有 400 参数错误、401 身份失效、403 权限拒绝等约定，不新增一套响应格式。

## POST /employees/export.xlsx

JSON 请求示例：

```json
{
  "query": "张",
  "departmentId": 3
}
```

文字与部门筛选和搜索接口一致，但导出全部匹配的授权行，不接受分页来截断导出。仍然最多 5000 行，超限使用既有 `409 EXPORT_LIMIT`，不能静默截断。

管理员包含工资列；查阅员完全没有工资列；员工和审批人只含本人匹配记录。XLSX 的字面文本单元格、防公式处理、MIME、附件下载、`nosniff`、`no-store` 与 M3 导出相同。无匹配记录时应生成仅包含合法表头的工作簿。

## 前端交互与资料保护

- 新列表筛选使用 POST body 传递姓名、工号等搜索内容，不将其写入 URL、路由 query/hash、浏览器持久化存储或日志。
- 前端仅在内存保存当前输入与已应用筛选。应用新筛选后回到第 1 页，翻页保持已应用条件；“按当前筛选导出”使用列表已应用的同一组条件，避免输入未提交时导出另一个范围。
- 不新增前端身份或权限体系。部门管理接口仍只开放 HR_ADMIN/HR_VIEWER；不能为员工下拉框开放全量组织数据。员工及审批人的筛选控件必须在其现有授权范围内设计。
- 搜索请求只读，可以取消旧请求并采用最新结果；不能让较慢的旧响应覆盖较新的筛选结果。退出登录或身份变化后清理内存中的搜索内容和结果。
- 本增量没有改变员工新增、编辑、导入、审批或附件操作的写入确认策略。

## 本轮验收要求

1. API：空条件兼容、Unicode 长度、姓名/工号/部门子串、字面通配符、精确部门及组合条件、分页边界、四角色范围和工资省略。
2. 导出：相同筛选与授权范围、表头及工资列、零匹配、5000 上限、防公式；旧 GET 接口回归。
3. 浏览器：筛选/清空/翻页/导出一致，快速切换条件无旧响应覆盖，URL 和持久化存储不含搜索资料；同时复验本轮部门编辑与暗主题修复。
4. 真实 MySQL 与实际浏览器由 QA 验收；单元测试或 CI 编译不能替代。结果写新报告，不覆盖 M1/M2/M3 历史证据。
